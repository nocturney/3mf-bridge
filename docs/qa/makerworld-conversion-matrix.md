# MakerWorld / Bambu 3MF conversion matrix (QA)

Scope: source 3MF files in MakerWorld/Bambu style -> **Orca** or **Prusa** targets only. No Cura,
ideaMaker, UP Studio, or Bambu targets. Nothing here changes the Go engine, the frontend, workflows,
or the version.

> **Read this first.** Nothing in this matrix is print-ready. A PASS means the file structure and the
> SliceBridge comparator agreed on one conversion run on one machine. It does not show that the output
> opens in PrusaSlicer or OrcaSlicer, that colours or nozzle are right, or that anything prints.
> Physical QA on the real printer is still required (see the checklist at the end).

## Provenance of the sources

- **None of the fixtures was downloaded from MakerWorld.** No network access was used. They are
  synthetic Bambu-style packages generated by `tests/make_fixture.py`, `tests/make-mixed-fixture.py`,
  `tests/make-nozzle-fixtures.py` and `tests/make_palette_fixture.py`. Each has one object, a 4-vertex
  tetrahedron, one build item and one plate. They are not representative of real MakerWorld models.
- Real MakerWorld downloads would give real coverage (multi-object, components, modifiers, supports,
  many plates, large meshes, real `slice_info`). Those files are not in the repo and were not fetched.

Expected vs observed, Prusa target:

- Geometry, build transforms, paint strings, object extruder, and the numbered colour list: matched
  (`tests/panda/panda_qa.compare` returned no problems for all 11 pairs).
- No stale G-code (`plate_1.gcode`, `plate_1.gcode.md5`) and no `UNSAFE_BAMBU_SCRIPT` in the output.
- Nozzle: source 0.2/0.4/0.6/0.8 gives output members that are **identical** (same XML, same JSON). The
  nozzle is dropped. `native/prusa_engine.go` says the printer model is "deliberately not chosen" and the
  user picks it in PrusaSlicer, so this looks intentional, but it does not preserve the nozzle.
- Layer height: `overheight` (0.16) and `nozzle-0.2` (0.10) produce identical output. Not carried.

## Gaps (true, with why)

1. **Orca target is untested locally.** The Go adapter needs a Go toolchain (`native/go.mod` says Go 1.25,
   `engine/go.mod` says 1.24.7) and `third_party/bl2std`, which is an empty submodule here. The only Orca
   evidence is `go test` in `native.yml` on Windows and macOS. Its result is not verified here. The smoke
   has no Orca runner, so Orca is always UNTESTED in it.
2. **Windows embedded sidecar not exercised.** `native/prusa_embedded_windows.go` extracts the EXE from the
   portable build. Only the vendored Python runner ran here. CI (`native.yml`) runs the contract on Windows
   and macOS.
3. **Compat harness defects (`tests/compat`, not changed here).**
   - It does not read `Metadata/SliceBridge_source_filaments.json`, which is where the Prusa output keeps
     its colour list. So `palette_slots` and `virtual_channels` FAIL on every Prusa output, even though
     `panda_qa` reads the same file and matches.
   - For a Prusa output, the JSON-only checks (`machine_scripts_not_carried`, `process_intent`) FAIL as
     "output project settings missing". Its own README says these are JSON-layout-only, so they should SKIP.
   - `tests/compat/README.md` points to `.github/workflows/conversion-compat.yml`, which does not exist. The
     compat unit tests are not run in CI.
4. **Prusa output has no PrusaSlicer-readable filament or printer config here.** The output has
   `Slic3r_PE_model.config` and the SliceBridge JSON, but no `Slic3r_PE.config`. Whether PrusaSlicer shows
   the colours or extruders correctly is **untested**. Physical or PrusaSlicer-import QA is needed.
5. **Nozzle and layer height are not carried into the Prusa output** (see above). Whether that is acceptable
   is a product decision, not something the tests can settle.
6. **Fixtures are too simple.** One object, 4 triangles, one plate, no components, supports, modifiers or
   multi-plate projects. The `overheight` fixture is not taller than the 0.2 fixture. Five-colour paint
   uses only slots 1 and 5.
7. **Paint codec is inferred.** The `4/8/C/1C/2C` mapping came from repo generators, not from the upstream
   Bambu codec, so a paint channel result is only as good as that inference.
8. **No MakerWorld sources.** Real downloads were not fetched. Add them under `tests/fixtures` (or a
   separate directory) before claiming MakerWorld coverage.

## Physical QA checklist (required before any printer use)

- Open the Prusa output in PrusaSlicer. Confirm the object, extruder assignment, and colours or materials.
- Open the Orca output in OrcaSlicer, once an Orca target can be produced.
- Confirm the printer model and nozzle the user selects match the physical hardware.
- Slice and review the preview. Do not print from this matrix alone.
- Print a test object on the real printer and check the multi-colour result against the source.

## Smoke script

`tests/makerworld/smoke_conversion.py` checks each source's package shell, converts each fixture to a
temporary directory with the Panda engine (only if an engine is found), and runs the SliceBridge comparator.
Outputs never go into the repo. It prints `PASS`, `FAIL`, or `UNTESTED` (with the reason) for each
source/target pair, and always prints the physical-QA disclaimer. Exit codes: `0` no FAIL, `1` a FAIL,
`2` with `--strict` and any UNTESTED. Engine discovery order: `SLICEBRIDGE_PRUSA_ENGINE`, then
`dist/prusa-sidecar`, then the vendored runner (needs `lxml` in the same interpreter).
